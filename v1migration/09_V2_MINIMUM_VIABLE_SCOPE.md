# Jarvis V2 — Minimum Viable Scope

> Migration Knowledge Base · Document 09  
> Produced: 2026-07-04 · Source: V1 analysis, lessons learned, product gaps

---

## Overview

This document defines the minimum viable scope for Jarvis V2 — what must exist for V2 to be considered a meaningful improvement over V1, and what must work end-to-end before V2 is declared complete.

The principle is simple: **do less, but do it completely**.

V1 tried to do too much. It has 11 Android screens, two competing brief generators, five nearly identical category screens, a broken daily brief, and an unreliable scheduler. V2 must do fewer things perfectly.

---

## Core Definition

V2 is complete when a user can:

1. Wake up each morning and receive a Daily Brief on their Android phone that is accurate, fresh, and generated by the system (not assembled from templates)
2. Capture a thought, reminder, or todo via voice in under 5 seconds
3. View all pending tasks with due dates and complete them
4. Know their monthly spending, income, and top expense categories from the brief or the finance screen
5. See school events and appointment reminders captured automatically from WhatsApp and SMS

If all five of these work — reliably, every day — V2 is a success.

---

## Out of Scope for V2

The following items are explicitly OUT of scope for V2. They are not V3 scope — they are simply not V2 scope. They should not be built during the V2 period.

| Feature | Reason |
|---------|--------|
| Real-time signal delivery (replace file-based upload) | V2 uses the existing file-based mechanism — works, not broken |
| Event bus / message queue | V2 uses sequential pipeline — sufficient for single-user load |
| ML-based merchant learning | V2 uses rules engine + LLM fallback — sufficient |
| Multi-currency support | INR only for V2 |
| Credit card statement parsing | Requires integrations that are not available |
| Portfolio / investment tracking | Out of scope — Zerodha has an app |
| Weather / calendar integration | Out of scope — too many external dependencies |
| Voice transcription accuracy improvement (fine-tuning) | V2 uses Whisper or Google STT as-is — sufficient |
| Web dashboard (Streamlit) redesign | Dashboard is a debugging tool, not a user product |
| Spouse financial analysis | Spouse onboarding is in scope; full financial analysis of spouse data is V3 |

## V2 Feature Scope

### Feature V2-01 — Daily Brief (End-to-End Fix)

**What is required:**
- [ ] Remove `daily_brief_generator.py` (deprecated, crashes)
- [ ] Remove `supabase_sync_service.py` (deprecated, crashes)
- [ ] Verify `DailyBriefAgent` generates and writes to `daily_briefs` Supabase table correctly
- [ ] Build `GET /briefs/latest` API endpoint
- [ ] Build `GET /briefs/{date}` API endpoint (brief history)
- [ ] Update `InsightSyncWorker` to call brief API and store in Room `daily_briefs`
- [ ] Update `DailyBriefScreen` to display the stored remote brief (not local template)
- [ ] Add push notification when morning brief is generated
- [ ] Fix scheduler to schedule `run_consumer_sync` as a recurring job (currently: runs once at startup)
- [ ] Add scheduler retry: if morning brief fails at 06:00, retry at 06:05, 06:10, 06:15
- [ ] Add brief delivery verification (server logs whether Android received the brief)

**Definition of Done:**
Every morning at 06:00, a brief is generated, stored in Supabase, delivered to the Android app, and a push notification alerts the user. The brief is fresh (generated from that morning's data). This works every day without manual intervention.

---

### Feature V2-02 — Voice Capture

**What is required:**
- [ ] Add a Capture screen to the Android app (accessible from all screens via floating action button)
- [ ] Implement tap-to-speak recording (use Android SpeechRecognizer or Whisper)
- [ ] Send transcribed text to backend API endpoint `POST /capture/voice`
- [ ] Backend processes captured text as an ACTION signal (creates a todo) or MEMORY signal (creates a fact), or stores as a general note
- [ ] Voice captures appear in the next Daily Brief

**Definition of Done:**
User taps a microphone button, says "Remind me to pay the water bill by Thursday", and this appears as a todo item in the app within 60 seconds.

**LLM Processing for Voice:**
Voice captures are routed through the Signal Understanding Agent with `source: voice_capture`. The SUA extracts the intent (ACTION for reminders, MEMORY for facts, etc.) and creates the appropriate downstream record.

---

### Feature V2-03 — Todo Management (Lifecycle Fix)

**What is required:**
- [ ] Fix todo/todo_items naming inconsistency (reconcile `todos` vs `todo_items` table naming in Supabase)
- [ ] Implement swipe-to-complete in `TodoScreen.kt`
- [ ] Implement snooze (24 hours) in `TodoScreen.kt`
- [ ] Implement auto-close: when a payment SMS confirms payment of a bill, find and close the related bill-due todo
- [ ] Basic duplicate detection: same bill alert on different days should update the existing todo, not create a new one
- [ ] Push notification for todos due today (already works — preserve)
- [ ] Add push notification for todos due tomorrow

**Definition of Done:**
The todo list is accurate. Completed bills close automatically. Snooze works. The todo count in the brief is honest.

---

### Feature V2-04 — School Events (Dedicated Handling)

**What is required:**
- [ ] Define a `school_event` sub-type within the FYI event category
- [ ] Identify school-related signals (WhatsApp group sources, sender patterns, keywords) and tag them as `school_event`
- [ ] School circulars → `school_event` type FYI
- [ ] School fee reminders → TODO with category `SCHOOL`
- [ ] Parent meetings / events → TODO with category `SCHOOL`
- [ ] Add school section to the Daily Brief (separate from general FYIs)
- [ ] Remove SchoolScreen.kt as a standalone screen — replace with school filter in FYI screen

**Definition of Done:**
A WhatsApp message about a parent-teacher meeting on July 10 appears in the morning brief under "School" with the date, and creates a todo "Parent-teacher meeting — Charan — July 10".

### Feature V2-05 — Android UI Simplification

**What is required:**
- [ ] Remove FamilyScreen.kt as standalone screen
- [ ] Remove SchoolScreen.kt as standalone screen
- [ ] Remove TravelScreen.kt as standalone screen
- [ ] Remove HealthScreen.kt as standalone screen
- [ ] Remove ShoppingScreen.kt as standalone screen
- [ ] Add category filter to FYI screen (dropdown: All, School, Family, Travel, Health, Shopping)
- [ ] Simplify bottom navigation to 4 items: Home (Brief), Todos, Finance, Capture
- [ ] FYI feed accessible from Home screen (Recent Updates section)

**Definition of Done:**
The app has 4 primary screens. The user finds everything they need in 2 taps.

---

### Feature V2-06 — Spouse Onboarding

**What is required:**
- [ ] Document how Shobana can install JarvisCollector on her device
- [ ] Signal upload identifies device/user (add `device_owner` field to upload payload)
- [ ] Consumer service accepts and processes signals from `shobana/` prefix (or tagged device)
- [ ] Shared todo space: todos created from Shobana's signals are visible to both
- [ ] Daily Brief includes a section for Shobana's recent signals (if any)
- [ ] Financial signals from Shobana's bank SMS are processed and appear in the shared financial summary

**Definition of Done:**
Shobana installs the app. Her SMS signals flow through the pipeline. Her bank transactions appear in the household financial summary. School-related WhatsApp messages from her phone are captured.

---

### Feature V2-07 — Financial Brief Quality

**What is required:**
- [ ] Daily Brief shows: salary received this month (yes/no + amount + date), lifestyle spend MTD, top 3 spending categories with amounts, investment total
- [ ] Label financial data visibility scope: "Based on bank SMS only. Wallet and card spend may not be included."
- [ ] Deploy missing Supabase migrations: `transfer_pairs`, `salary_sources` tables
- [ ] Bootstrap salary registry from last 6 months of transaction history (one-time run)
- [ ] Expand NACH/SIP keyword patterns to improve investment classification

**Definition of Done:**
The financial section of the brief is accurate enough that the user trusts it. The label "Based on bank SMS only" sets honest expectations.

---

### Feature V2-08 — Operational Reliability

**What is required:**
- [ ] Add `run_consumer_sync` as a recurring scheduler job (every 15 minutes)
- [ ] Add `pipeline_runs` table to Supabase — record every pipeline run with status, signal count, duration
- [ ] Add `system_status` table to Supabase — pipeline lock
- [ ] Remove `_instrumented_ask` mock from `pipeline_orchestrator.py`
- [ ] Brief scheduler retry logic (3 retries, 5-minute intervals)
- [ ] Config migration: move family names, priorities from JSON files to Supabase `user_preferences` table (with read fallback to JSON for backward compatibility)
- [ ] Remove `signal_processor.py` (legacy monolithic pipeline)
- [ ] Remove shadow mode from `signal_understanding_agent.py`

**Definition of Done:**
The system runs 24 hours without manual intervention. Pipeline runs are logged. Failed jobs retry automatically. The mock is gone.

## V2 Priority Order

Build in this sequence. Each item depends on the previous.

| Priority | Feature | Why This Order |
|----------|---------|---------------|
| 1 | **V2-01 — Daily Brief** | Highest-value output; all other features feed it |
| 2 | **V2-08 — Operational Reliability** | Brief delivery requires reliable scheduling |
| 3 | **V2-02 — Voice Capture** | Core V2 differentiator; no V1 equivalent |
| 4 | **V2-03 — Todo Lifecycle** | Brief quality depends on accurate todos |
| 5 | **V2-04 — School Events** | Highest-value FYI improvement |
| 6 | **V2-05 — Android UI Simplification** | Reduces confusion; simpler to maintain |
| 7 | **V2-06 — Spouse Onboarding** | Doubles system value |
| 8 | **V2-07 — Financial Brief Quality** | Improves financial section of brief |

## V2 Architecture Requirements

### Must Preserve from V1

| Component | Why |
|-----------|-----|
| `SignalQualificationAgent` | Validated, correct, no known bugs |
| `SignalUnderstandingAgent` (after removing shadow mode) | Correct; deterministic + LLM hybrid is the right design |
| `FinancialAgent` | Validated, locked algorithms (4-condition transfer, 4-tier salary, refund semantics) |
| `AggregationService` | Idempotent, correct |
| `TodoAgent` | Working — needs lifecycle additions only |
| `FactAgent` | Working |
| `FyiAgent` | Working |
| `DailyBriefAgent` (core) | Correct — fix delivery path, not the generator |
| Canonical signal contract | Locked interface — no downstream agent may parse raw messages |
| One-owner-per-table constraint | Locked architectural constraint |
| LLM classification cache | Performance optimisation worth preserving |
| Financial preservation override | Safety net — cannot be removed |
| Pre-seeded merchant registry | Cold start protection |

### Must Build for V2

| Component | Why |
|-----------|-----|
| `GET /briefs/latest` API endpoint | Brief delivery |
| `POST /capture/voice` API endpoint | Voice capture |
| Voice capture screen (Android) | Voice input |
| Brief-aware `InsightSyncWorker` | Brief delivery to Android |
| School event classifier | School event dedicated handling |
| `pipeline_runs` table (Supabase) | Operational observability |
| `system_status` table (Supabase) | Pipeline locking |
| Spouse device support | Multi-user signals |

### Must Remove from V2

| Component | Why |
|-----------|-----|
| `services/daily_brief_generator.py` | Deprecated; crashes |
| `services/supabase_sync_service.py` | Deprecated; crashes |
| `services/signal_processor.py` | Legacy monolithic pipeline |
| `services/financial_intelligence.py` | Not V2-aligned; superseded |
| `_instrumented_ask` mock in `pipeline_orchestrator.py` | Production mock; must be removed |

| `FamilyScreen.kt`, `SchoolScreen.kt`, `TravelScreen.kt`, `HealthScreen.kt`, `ShoppingScreen.kt` | Duplicate code; consolidate into FYI with filters |
| Local brief assembly in `InsightSyncService.kt` | Conflicts with server-generated brief |

## V2 Definition of Done (System Level)

V2 is complete when all of the following are true:

1. **Brief**: Morning brief generated daily at 06:00, delivered to Android within 10 minutes via push notification, displaying server-generated content (not local template). This works for 30 consecutive days without manual intervention.

2. **Voice**: User taps the microphone button, speaks a reminder, and it appears as a todo within 60 seconds.

3. **Todos**: Todo list is accurate. Completed bill payments close their corresponding bill-due todos automatically. Duplicate detection prevents same todo from appearing twice.

4. **School**: Parent-teacher meetings, school events, and fee reminders captured from WhatsApp appear in the School section of the morning brief.

5. **Finance**: Morning brief shows: salary status, lifestyle spend MTD, top 3 categories, investment total. Financial data labelled with visibility scope.

6. **Spouse**: Shobana's device signals are captured, processed, and appear in the shared brief and todo list.

7. **Reliability**: Pipeline runs 7 consecutive days without manual restart. Consumer sync runs every 15 minutes. Failed jobs retry. All runs logged to `pipeline_runs`.

8. **No legacy code**: All deprecated, broken, and legacy components removed. `_instrumented_ask` mock is gone. `signal_processor.py` is gone. `daily_brief_generator.py` is gone.
