## Section 1 – End-to-End Flow

The pipeline executes sequentially in three stages using the Supabase remote database. Below is the logical dataflow showing how a raw record propagates through the qualification stage:

```text
       [ Supabase Table: mobile_signals ] (processed = false)
                      ↓
              [ Record Selection ]
                      ↓
    [ SignalQualificationAgent.qualify_signal() ]
      - Age Check (90 days stale limit)
      - WhatsApp Pre-July Exclusion
      - OTP and System Noise Filters
      - Telecom Promos & Ignore Lists
      - Family & High-value Boosts
      - Financial Preservation Overrides
                      ↓
       [ Score & Status Classification ]
         - Score <= 20: REJECTED
         - 21 <= Score <= 59: REVIEW
         - Score >= 60: QUALIFIED
                      ↓
    [ Supabase Table: qualified_signals ] (Insert outcome)
                      ↓
     [ Post-Qualification DB Updates ]
       - Mark mobile_signals.processed = true
```

### Components Participating in Flow

1. **Entry Point & Orchestrator**: `scripts/run_pipeline_backfill.py`
   - Selects unprocessed records from `mobile_signals`.
   - Iterates through the batch, instantiates the Qualification Agent, and calculates scores.
   - Performs bulk insertion into `qualified_signals` and updates the `processed` flag in `mobile_signals`.
2. **Qualification Agent**: `src/agents/consumer/qualification_agent.py`
   - Houses the `SignalQualificationAgent` class containing the scoring and exclusion algorithms.
3. **Configuration Configs**:
   - `config/qualification_rules.json`: Thresholds, boosts, and preservation keywords.
   - `config/family_context.json`: Spouse, children names, and relation keywords.
   - `config/high_value_domains.json`: High value domain categories (finance, medical, education, etc.) and keyword mappings.
   - `config/jarvis_rules.json`: Ignore topics and conditional filters.
4. **Database Layer**: Supabase remote client targeting the `jarvis_insights_schemav1` schema.

## Section 3 – Record Selection Logic

### What query is executed?
The orchestrator executes the following Python Supabase Postgrest query:
```python
client.table("mobile_signals").select("*").eq("processed", False).order("id").execute()
```

### What filters are applied?
* `processed = False`: Selects only raw records that have never been qualified.
* Ordered by `id` ascending to maintain ingestion sequence.
* No source or date filters are applied at query time; all historical records are retrieved.

### What fields are retrieved?
Since `select("*")` is used, the following fields are retrieved:
* `id` (bigint PK)
- `device_id` (text)
- `source` (text)
- `sender` (text)
- `message` (text)
- `mobile_timestamp` (timestamptz)
- `processed` (boolean)
- `created_at` (timestamptz)
- `message_hash` (text UK)
- `metadata` (jsonb)

## Section 5 – Qualification Decision Logic

### Decision Tree & Rule Hierarchy
The qualification scoring workflow proceeds as follows:

```text
                          Start
                            │
              Stale Age > 90 days? ───────────► YES ──► REJECTED (STALE_SIGNAL)
                            │ NO
         WhatsApp Pre-July (< 2026-07-01)? ──► YES ──► REJECTED (excluded_pre_july_whatsapp)
                            │ NO
                     OTP Message? ────────────► YES ──► REJECTED (otp_message)
                            │ NO
                WhatsApp System Noise? ───────► YES ──► REJECTED (whatsapp_system_noise)
                            │ NO
                   Telecom Promo? ────────────► YES ──► REJECTED (telecom_alert)
                            │ NO
                  Ignore Topic Match? ────────► YES ──► REJECTED (ignore_topics)
                            │ NO
                Conditional Ignore Match? ────► YES ──► REJECTED (conditional_ignore_topics)
                            │ NO
                     Is Promo Code? 
                            │ YES ──────────────────────────────────────┐
                            │ NO                                        ▼
                   [Base Score = 40]                        Has Financial Keywords?
             - Family Context Match? (+30)                      │ YES            │ NO
             - High Value Domain?    (+30)                      ▼                ▼
                            │                          [REVIEW (score 25)]   [REJECTED]
                            ▼
             WhatsApp Group/Community Msg? ──► YES ──► [REVIEW (score 30)]
                            │ NO
                     Final Score <= 20? ──────► YES ──┐
                            │ NO                      │
                     Final Score <= 59? ──► YES ─► [REVIEW]
                            │ NO                      │
                            ▼                         ▼
                       [QUALIFIED]          Has Financial Keywords?
                                                │ YES            │ NO
                                                ▼                ▼
                                            [REVIEW]         [REJECTED]
```

### Weightings and Usage
The decision logic uses raw signal components with the following weighting:
* **Message Text (Weight: 80%)**: Primary string matching for ignore lists, OTP keywords, family names, and high-value domains.
* **Source Type (Weight: 10%)**: Used to trigger specific WhatsApp exclusion and system noise checks.
* **Sender (Weight: 5%)**: Used to filter out group/community notifications.
* **Timestamp (Weight: 5%)**: Used for age filtering and WhatsApp pre-July cutoff checks.
* **Metadata (Weight: 0%)**: Not read or considered in any capacity.

No LLM is utilized in the qualification stage; the process is fully deterministic.

### LLM Call Analysis (End-to-End Pipeline)

While the **Qualification stage is 100% deterministic** and makes no LLM calls, the downstream stages of the backfill pipeline rely on LLM inference. Here are the specific areas where LLM calls are made:

1. **Signal Understanding Agent (SUA) - Classification & Extraction**
   - **File**: [agent.py](file:///home/user/petprojects/ai/jarvis/src/agents/sua/agent.py)
   - **Function**: `SignalUnderstandingAgent.understand_signal()`
   - **Details**: 
     - Once a signal passes qualification with a `QUALIFIED` status, it is eligible for the SUA stage. 
     - The SUA performs a deterministic noise check first. If it is not categorized as noise, it constructs a prompt containing the message sender, source type, timestamp, and body.
     - An LLM call is executed via `self.llm_client.ask(prompt)` targeting the local Ollama instance (port `11434`) running the `qwen2.5:1.5b` model.
     - The LLM is requested to classify the signal into one of five categories (`FINANCIAL`, `ACTION`, `FYI`, `FACT`, `NOISE`) and extract type-specific metadata (e.g., amount, merchant, task name, due dates) as a JSON object.
     - **Fallback**: If the LLM call fails or times out (30-second threshold), the agent catches the exception and falls back to deterministic rule-based heuristics (`_fallback_understand`).

2. **Downstream Agents (Stubs in Phase 2B)**
   - **Files**: [src/agents/stubs/](file:///home/user/petprojects/ai/jarvis/src/agents/stubs/) (`financial_agent_stub.py`, `todo_agent_stub.py`, `fyi_agent_stub.py`, `fact_agent_stub.py`)
   - **Details**: Downstream agents in the current Phase 2B framework are stubs and do not make LLM calls. They consume the JSON contract produced by the SUA.

## Section 8 – Canonical Payload Assessment

### Does a complete signal payload survive qualification?
**NO.** 

### What information is permanently lost?
1. **Device Attribution (`device_id`)**: The ID specifying which device uploaded the signal (e.g. `family_member_1` vs `user`) is dropped. Downstream agents are forced to guess context based on message body text, violating the multi-device design.
2. **Collector Metadata (`metadata`)**: Rich transaction metadata (the precise numerical amount, reference IDs, transaction currencies, and verified counterparty names) parsed from PDF statements or Google Pay logs in Phase 1B is **permanently discarded**.

### Examples from Sample Records

#### Example 1 (Sample Payment A)
- **Original Message**: `Paid to Sample Counterparty A`
- **Original Metadata**: `{"amount": 50.00, "currency": "INR", "transaction_type": "DEBIT", "payment_channel": "UPI"}`
- **Qualified Signal Result**: Mapped strictly to message text (`Paid to Sample Counterparty A`). The `$50.00` value is lost.
- **SUA Contract Output**: The SUA processes the raw string `Paid to Sample Counterparty A`. Having no amount keyword in the text, it extracts **`amount: Paid`** (an invalid string). Lineage is broken, and downstream financial rollups receive invalid data.

#### Example 2 (Sample Payment B)
- **Original Message**: `Paid to SAMPLE RESTAURANT`
- **Original Metadata**: `{"amount": 420.00, "currency": "INR", "transaction_type": "DEBIT", "payment_channel": "UPI"}`
- **Qualified Signal Result**: Mapped strictly to text.
- **SUA Contract Output**: The LLM guesses the amount as **`$50`** based on other context, corrupting the actual spend value.

## Section 9 – Downstream Impact

* **Signal Understanding Agent (SUA)**: Severe impact. Because structured collector metadata is stripped, the SUA is forced to perform expensive and unreliable LLM extraction or rule fallbacks on raw message text. When raw text lacks numeric figures (common in PDF line extractions), the LLM hallucinates amounts, currencies, or marks them null.
* **Financial Agent**: High impact. The financial ledger (`financial_facts`, `financial_events`) receives corrupted amounts (e.g., `"Paid"` or hallucinated `$50` values), making income, spend, and category calculations invalid.
* **Todo, FYI, Fact, & Memory Agents**: Medium impact. They cannot verify which family member (`device_id`) generated the action or FYI, preventing personal task assignment.
* **Replay Capability & Lineage**: Broken. Because the unique `message_hash` and `metadata` are dropped at the qualification stage, it is impossible to replay a downstream routing action using original collector inputs. Lineage is broken at the `mobile_signals → qualified_signals` boundary.

## Section 10 – Recommendations

| Rank | Issue | Recommended Resolution |
|---|---|---|
| **CRITICAL** | Discarded Ingestion Metadata | Add `metadata` (jsonb) column to `qualified_signals` table and map it directly from `mobile_signals.metadata` during insert. |
| **CRITICAL** | Lost Device Attribution | Add `device_id` (text) column to `qualified_signals` table to preserve the origin context of who sent the signal. |
| **HIGH** | SUA Contract Extraction Gap | Update `SignalUnderstandingAgent` to read core fields (`amount`, `currency`, `counterparty`) directly from `qualified_signals.metadata` when available, completely bypassing LLM guessing for structured collector records. |
| **MEDIUM** | Inefficient Processed Flag Updates | In the orchestrator, update the `processed` flag in `mobile_signals` in bulk using `.in_("id", chunk_ids)` to prevent individual HTTP requests. |
| **LOW** | Missing Trace Identifiers | Propagate a `run_id` or unified trace identifier downstream so signal lineage can be audited from `mobile_signals` to `signal_routes` easily. |
